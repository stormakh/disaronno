Why Rust kept memory after the sync, and the fix

Three short runs of Rust on the same account, each with a full history sync, measured 4 minutes after the sync. The allocator counts show that almost all of the memory was free memory that glibc kept, not data that the client held. There were no huge pages.

BuildMemoryPrivateHeap in useHeap free, keptPeakNo socket
No fix38.0 MB31.8 MB2.0 MB31.3 MB38.1 MB10.9 MB
Fixed mmap threshold33.1 MB27.0 MB1.9 MB25.1 MB37.1 MB7.7 MB
Fixed threshold and trim when a lane is idle14.3 MB8.1 MB1.6 MB24.5 MB37.1 MB7.5 MB
  • Fixed mmap threshold: glibc raises its mmap threshold each time a large block is freed. Then the large buffers of a sync come from a thread heap and stay in RAM. The socket now sets the threshold to the glibc default, so that the threshold stays fixed.
  • Trim when a lane is idle: the blocks of a decoded history chunk are small. glibc gives back only the top of a heap, and a few long-lived blocks keep the rest. When a lane has had no work for 5 seconds, the socket calls malloc_trim, once after each burst of work.
  • What is left, 4 minutes after the sync: about 6.5 MB of program code, which the kernel later removes in part (see the 4-hour run above), and a heap of about 7.5 MB that holds 1.7 MB of live blocks spread over its pages. A trim cannot give back a page that holds a live block. "No socket" is the memory after logout, with the socket dropped and a trim.
  • Cost: on the mock live flow, the Rust peak went from about 4.7 MB to about 5.0 MB, because the code layout moved. Both settings apply to Linux with glibc only. Each sync is a little different, so the "No fix" row and the other rows did not get exactly the same data.

What these numbers do not prove

  • Real WhatsApp: one real account linked, did a full history sync, received live messages and logged out. No test sent a real message or transferred media through the socket. The other client flows ran against a local mock server.
  • Long run: this is one 4-hour run, not weeks. About 150 live messages arrived after the sync, so a leak that grows slowly per message may not show. The clients stored no messages, sent none and transferred no media. An app does these things and uses more memory. The Baileys growth is not proof of a leak, because a later garbage collection can free it.
  • TLS: the live flow uses ws://, with no TLS. One real connection to WhatsApp passed the real certificate check, reached the QR step, and peaked at 5.1 MB. A logged-in client over TLS will use more than the flow number.
  • Memory settings: the static build and function ordering apply to the binaries in this workspace, and the bench uses the system allocator. A program that depends on this crate must set these itself, or it uses more memory. With mimalloc, the compact form is 11.1X, under 12X.
  • Host lookups: the static build reads only /etc/hosts and /etc/resolv.conf. It ignores other system lookup modules, such as mDNS.
  • Compact form: each read costs one full decode. It is a separate type for held messages, not the normal message type.
  • Compression: nothing here uses compression or shares data between messages.
  • Different behavior: work that Baileys starts at the same time runs in order on two queues. Protobuf and binary node decode reject input with more than 64 nested levels, so that a peer cannot crash the process.
  • Tests: 407 of 407 is a count of named tests. A second review found that a concurrent Noise test became sequential, a string-in-long-field test became a parsing test, and three upstream token tests check only their own setup. Upstream's 4 live end-to-end test files did not run and are not in this count.
  • Not ported: proxy agents and uploadWithFetch. Image and audio work uses ffmpeg in place of sharp, jimp and music-metadata.
